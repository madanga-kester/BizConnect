# Mabiz Implementation Plan

> **Historical plan:** The scope below records earlier frontend-only planning decisions and is not the current implementation status. Stages 2 and 3 are now implemented; see [`docs/STAGE2_BACKEND.md`](docs/STAGE2_BACKEND.md) and [`docs/STAGE3_BUSINESSES.md`](docs/STAGE3_BUSINESSES.md) for current backend/API boundaries and verification.

## Approved scope and technical approach

Implement the full original Mabiz specification together with all 13 additional requirement groups, without removing the social feed, discovery, business profiles, management, stories, video, catalogs, messaging, account, notification, search, or moderation capabilities. This is a frontend application built on the initialized Expo Router + React Native + TypeScript + NativeWind starter for Android and iOS. Keep the starter's generated `appSlug`, deep-link scheme, and native bundle identifiers unchanged. Use the available Expo Web/Preview as a runtime and interaction surface; it does not substitute for a native camera, location, notification, or device acceptance check.

Use Expo Router route groups for the five persistent main tabs—Home, Discover, Create, Stories, Profile—and linked secondary routes for business/profile details, video, search, messaging, notifications, catalogs, business setup/management, team, verification, milestones, analytics, ideas/opportunities, privacy/security, data export/deletion, help, guidelines, and saved/recent content. Screens compose reusable feature components and do not embed seed data.

Use strongly typed domain models and uniform page/result/error contracts. Put all realistic Kenya-focused seeds in dedicated data modules. Separate presentation from domain-oriented service adapters; adapters are explicitly local mock implementations and never claim to persist to a server. Persist user choices and demo records locally where suitable, and reserve SecureStore for session-secret material. Make auth state, roles, business identity switching, Owner/Administrator/Content Manager authorization checks, and per-business records explicit in the client model. Use async mock boundaries to make future ASP.NET Core REST/SignalR adapters replaceable without rewriting screens. Document that no server, database workflows, or payments are being implemented by this client task; the fixed managed starter's preinstalled server infrastructure is not a product backend.

Add centralized English/Swahili translation resources, Kenya locale/currency/phone/date utilities, and a structure extensible to further African locales. Use Expo image caching and local photo compression, initial-feed pagination, reduced-data/autoplay settings, permission prompts at point of use, and useful offline/loading/empty/success/error states. In this frontend-only demo, selected media remains on-device; full viewport-based lazy loading and resumable/retryable upload transport remain future work, not implemented behavior. Clearly label startup costs as estimates and user stories as user-submitted; only an explicit approved state receives a business verified badge.

## Project structure

- `app/`: Expo Router root and tab layouts, five primary tabs and connected nested routes.
- `components/`: reusable navigation, forms, cards, identity badges, post/story/product/business components, and feedback/loading/empty/error states.
- `hooks/`: the persisted local demo store and sign-in gating for protected actions and screens.
- `lib/api/`: API configuration, contracts, common errors and future adapter interfaces; `lib/services/` contains local mock adapters.
- `data/`: coherent Kenyan seed fixtures for users, businesses, products, services, posts, stories, videos, opportunities and messages.
- `types/`: strongly typed domain, request, response, pagination, session and permission models.
- `i18n/` and `utils/`: centralized translations, Kenyan formatting, validation, location and access-control helpers.
- `assets/images/`: Mabiz launcher, splash and platform icon assets.
- `docs/`: architecture and future ASP.NET Core/SignalR integration notes, including upload/auth and pagination contracts.

## Design system

Use a confident editorial mobile identity: premium community-product design with warm, human founder storytelling and practical business-discovery controls. Core principles: discovery-led; trust without overclaiming; practical Kenyan context; restrained, legible mobile-first density. In Light, deep navy grounds navigation and text, emerald signals growth and explicit trust states, warm orange highlights actions, and a soft warm-white canvas keeps stories and product imagery vivid. In Dark, use a true-black canvas (#000000), neutral-charcoal surfaces (#0A0A0A–#171717), and neutral borders, with no green cast in large surfaces; preserve emerald and orange as concise brand accents. The bottom navigation background, border, labels and icons follow the selected scheme. Use consistent spacing and rounded surfaces, accessible contrast, and native system typography with a clear display/body/metadata hierarchy. Structure screens as vertically flowing editorial sections, horizontally browsable story/category rails, and compact business cards rather than a storefront grid. Signature motifs: a connected-link/leaf Mabiz mark, emerald verification/status treatments only when explicitly approved, and orange founder-story chapter markers. Interactions give immediate local feedback, disclose mock status where appropriate, and confirm destructive operations; animations are subtle (short opacity/scale transitions, no motion-heavy autoplay). Brand essence: “A local-first discovery and founder-learning network for people building and backing Kenyan businesses”—trustworthy, energetic, practical. Brand voice is direct and human: “Find the people behind the business.” “Small beginnings. Real business lessons.” Wordmark: custom linked-loop / sprout mark paired with the Mabiz name. Ownable signature color: deep emerald.

## Phase 2 implementation plan

### Inspection findings from the existing project

The Phase 2 inspection was completed against the existing Expo project, README, full TODO, plan, route tree, root/tab navigation, shared components, AsyncStorage/SecureStore state provider, typed domain models, seed fixtures, API configuration, mock adapter, integration documentation, and representative screens. The app is already a feature-rich Expo Router/React Native frontend; Phase 2 is a corrective and completion pass, not a rebuild. Baseline `pnpm check`, `pnpm lint`, `pnpm exec expo install --check` passed; `pnpm test` passed the existing 25 CORS tests while one inherited server-auth logout test remains explicitly skipped. No Mabiz-domain automated tests existed at audit time.

Confirmed gaps that guide, rather than duplicate, the implementation: hidden and blocked-content rules are applied on Home but not consistently on video, search, business/person detail, and all message/action paths; store mutations can create local reports repeatedly and can send/start conversations without a single shared policy boundary; sign-up marks a user authenticated before the demo OTP and accepts any six-digit value although the UI states `123456`; protected-route checks are distributed in screens without a root navigation session guard; the discovery “map” is a location-card preview, correctly lacking geographic coordinates, and there is no followed-business filter; the root API contracts expose only a generic adapter marker alongside paginated local reads; and the existing integrations guide is under `docs/backend-integration.md` rather than the requested root `API_INTEGRATION.md`.

### Targeted implementation

1. Extract pure, typed policy and validation helpers for feed visibility, blocked/private profiles, message permissions, registration/login/OTP validation, combined discovery filtering, report deduplication, and business role authorization. Use the same rules from visible screens and state mutation entry points; keep local state authoritative only for the demo.
2. Harden persisted local actions: make hide/block/unblock and like/follow/save interactions immediately consistent; keep hidden posts hidden on every relevant public surface after navigation/restart; prevent blocked/private content from leaking through search, feed, videos, profiles, comments or conversations; prevent unauthorized message start/send; make report submission idempotent for an active matching report; add mark-all-read; and retain explicit local-only moderation/message notices.
3. Make onboarding a real staged demo flow: validate required registration fields and matching password confirmation; add password visibility; do not persist passwords; accept only the documented demo OTP without claiming SMS delivery; issue a local session after verification and required profile setup; expire a session while the app is open as well as at hydration; clear session credentials on logout; and centrally redirect unauthenticated direct navigation from private routes while leaving public browsing available. Keep the mock-vs-future ASP.NET Core Identity/JWT boundary explicit.
4. Extract discovery filter/sort behavior so query, category, county, town, neighbourhood, coarse nearby area, price, rating, verified/new/popular/followed filters compose, and keep empty/error/loading feedback. Because the current fixture has no coordinates and an Expo-compatible real map cannot be verified here, retain the location list and plainly label map mode as a temporary map-unavailable fallback; do not fabricate coordinates or claim a geographic map exists.
5. Preserve existing business identity, ownership, team, catalog, feed, drafts, story, moderation, messaging and notification features; guard sensitive operations at both screen and store/service boundaries without removing public read-only views. Verify active business selection reaches the correct business data, team roles control available actions, content remains editable, and data changes stay local.
6. Add explicit typed feature service/request/response interfaces and stable mock service boundaries for authentication, users, businesses/memberships, discovery, feed/posts/reactions/comments, catalog, stories, messaging, notifications, verification, moderation and media upload progress/cancel/retry/resume. Provide future media transport contracts only; do not simulate a real upload, backend, push service, SignalR server, or existing endpoint.
7. Add `API_INTEGRATION.md` with expected .NET 10 LTS backend domains, proposed—not existing—REST endpoint contracts, request/response and error examples, auth/JWT refresh, pagination, file-upload and progress/resume/cancel, SignalR, notifications, moderation and local-mock boundaries. Update README/TODO accurately.
8. Add meaningful Vitest suites for actual Mabiz rules and workflows (validation/session/guard, role/identity switching, business create/edit, discovery combination, visibility/blocking, follow/like/comment/save, draft/publish validation, messaging, reporting, and media selection error boundaries). Reuse fixtures and pure functions; no database/backend writes. Run TypeScript, lint, tests, Expo dependency check, app startup, Web export and Android/iOS JS bundle exports. Report those as exports, not native builds; only claim native EAS/device build or physical permission/video checks if actually executed.

## Phase 3: Native Mobile Completion and Frontend Stabilisation

### Scope and implementation decisions

Continue in the existing Expo Router / React Native / TypeScript project; do not rebuild the app and do not start the ASP.NET Core backend. Preserve all current local-demo functionality and continue to state that all actions remain local and are not server-synced. Keep Manus's port-8081 Expo Preview and port-3000 starter API distinction intact. The starter `server/`, Drizzle files, database dependencies, and generated Expo configuration are not Mabiz's future business backend; do not expose app features through them or delete starter infrastructure that the managed Mobile runtime needs. The owner confirmed that installed Expo Go is SDK 58 while Mabiz is SDK 57 and approved upgrading the existing project to SDK 58, aligning Expo-managed dependencies and applying only required migrations; keep identifiers, local-demo semantics and both fixed ports unchanged, and do not add backend work, native release builds or publishing.

Implement the native geographic Discover surface with SDK 58-compatible `react-native-maps`, plus a web-only accessible list fallback. Only use source-attributed public OpenStreetMap neighbourhood/district/city centroids as approximate area markers; never portray them as verified storefront coordinates or infer a business pin from its address text. Businesses without a matched public-area feature remain discoverable and are explicitly marked not mapped. A marker opens a business preview and detail route; map/list switching, current-area permission, denial fallback, blocked-owner filtering and combined filters continue to apply. Device validation remains necessary for native map rendering and gestures.

Stabilise native journeys through testable pure validation and platform-independent interaction tests plus Expo JS bundle checks. The shared `Page` uses the reported top inset directly and falls back to 59 px when the root still supplies its 16 px placeholder on native iOS or in a narrow embedded phone Preview; desktop Web and Android layouts remain unchanged. This keeps headers clear of the status bar and Dynamic Island/notch across Home, Stories and Profile. Virtualise the video feed so only the actually reported visible item can play, pause offscreen players, size cards to the screen and suppress autoplay under reduced-data mode. Inspect permissions, camera/gallery selection, video player errors, SecureStore, keyboard/focus, accessibility labels, responsive layouts, offline behavior and Android list/media performance. Do not state that physical-device behavior or a native release binary passed without an actual device or Dashboard build result. Keep native folders and caches generated/ignored per the existing managed Expo workflow; do not remove starter server/schema dependencies without a supported Mobile-template reason.

Treat the current `space.manus.Mabiz.t091153525322984` Android package/iOS bundle identifier and derived scheme as temporary managed starter identity. Do not guess the permanent reverse-domain application IDs or a production deep-link scheme; keep current IDs stable until the owner provides and approves them, then update Android, iOS, scheme, deep links and documentation together before release. A restricted build-time `GOOGLE_MAPS_API_KEY` conditionally enables the Android Google Maps config plugin; it remains unset until the final app ID and signing certificate are known. Prepare deterministic lockfile/install, config validation, Expo JS exports and documented Dashboard build handoff; native release builds must be run through the supported Dashboard flow, not EAS/Android/iOS tooling in this Sandbox.

### Delivery boundaries

The HTTP transport now supports JSON GET/POST/PUT/PATCH/DELETE, cancellation, request IDs, typed error envelopes, bearer injection and single-flight refresh; the typed production REST service factory maps proposed API routes, but no backend exists and the current screens are not migrated to those services. Social Stories, polls and listings have distinct service contracts and local mock adapter support; their route names are proposals pending backend review. Keep the app usable in its current local demo mode with clear device-only disclosures. Backend integration remains deferred until native/frontend stabilisation and API review are accepted. Physical-device tests and Dashboard native artifacts remain unverified. Permanent application identifiers and a restricted Android Maps key require owner input; exact business-premises coordinates remain unavailable, so map pins are labeled public-area estimates only.

## Phase 3.13 Create studio and Phase 3.14 implementation decisions

Retain the existing Create tab and make it the editorial launch point into existing route/state systems rather than building a parallel catalog. Use the shared local app store for demo publication, AsyncStorage persistence and identity/audience settings; keep personal posts, ephemeral Social Stories, permanent founder stories, polls, products/services, offers, events, opportunities, milestones and drafts as distinct typed models. Social Stories expire after at most 24 hours; Highlights preserve references to Stories and remain a separate display. Poll voting has one per-user response, supports configured multiple choice, rejects closed polls and reports response-based totals. Create and edit flows stay within current local state, validate date/price/media input and state that no remote account receives the content.

The production adapter seam is `MabizServices` with `SocialStoriesService`, `ListingsService` and poll voting added as typed mappings. The mock adapters hold isolated in-memory fixtures for API/service consumers; screen actions remain in the persisted app store for now. Production mode must never silently fall back to local success. New proposed paths and server requirements are documented in `API_INTEGRATION.md`; adapter presence is not backend availability. Real device permissions, durable upload, retry/resume and server-side audience enforcement remain backend/device integration work.

Creation-specific code is split among `app/(tabs)/create.tsx`, `app/create-social-story.tsx`, `app/create-listing.tsx`, `app/create-catalog-item.tsx`, `hooks/use-app-store.tsx`, `lib/api/feature-contracts.ts`, `lib/api/production-services.ts` and `lib/services/mock-services.ts`. Shared Story access policy is in `utils/social-story-privacy.ts`; coverage resides in `tests/social-story-privacy.test.ts`, `tests/api-adapters.test.ts`, the broader Vitest suite and `e2e/six-journeys.spec.ts`.
